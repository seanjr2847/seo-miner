# 화면별 문서

대시보드(`/capture dash {사이트}`)의 화면마다 한 장씩. 각 장은 같은 꼴입니다 —
**한 줄 설명 · 여기서 할 수 있는 것 · 여기서 얻는 것 · 유즈케이스와 그림 · 비어 보일 때**.

전체 흐름은 [사용 안내](../guide.md), 명령 목록은 [리포 README](../../README.md#명령)에 있습니다. 여기는
"이 화면 앞에 앉았을 때 무엇을 할 수 있나"에 답하는 자리입니다.

## 화면 (메뉴 순서)

메뉴(왼쪽 레일)는 화면을 **묶음** 아래 세웁니다 — 묶음 하나가 사용자의 질문 하나이자 한 번에
다시 재는 단위입니다. 묶음의 이름·단계·주기의 정본은 `skills/capture/scripts/run_all.py` 의
`GROUPS` 이고, 화면이 어느 묶음에 드는지는 각 뷰 `view-def` 의 `"group"` 이 말합니다. 그래서
여기에는 묶음 이름을 다시 적지 않습니다(두 벌이 되면 한쪽만 낡습니다). 잴 단계가 있는 묶음의
화면은 맨 위에 마지막으로 잰 날과 [이 묶음 다시 재기]를 달고, 전체 다시 재기는 [진행 안내] 한
곳에 있습니다.

| 화면 | 무엇을 하는 곳인가 |
|---|---|

| [관찰 중](hold.md) | 고친 페이지의 효과를 재는 동안 그 페이지의 새 기회를 미뤄 둔다 |
| [클릭 변화](analysis.md) | 클릭이 왜 늘고 줄었는지 원인별로 가른다 |
| [순위 상승 기회](keywords.md) | 1페이지까지 남은 거리를 깊이로 그리고, 무엇부터 손댈지 고른다 |
| [키워드 관리](kwmanage.md) | 어떤 검색어의 순위를 잴지(추적) 시장마다 켜고 끄고, 씨앗 키워드를 정한다 |

## 화면 안 탭 (modes)

화면은 머리 아래에 [처리]·[관리] 같은 탭 줄을 가질 수 있습니다. 선언은 그 화면 `view-def` 의
`"modes": [{"id", "label", "count"?, "hide_empty"?}]` 한 곳이고, 패널은 마크업의 `data-mode="<id>"` 로
자기 탭을 말합니다. 패널은 화면 상자로 옮겨지는 `<section>`/`.band` 이거나, 그 섹션 **안**의 `.card`
입니다(안쪽 버튼·칩의 `data-mode` 는 이 틀의 것이 아닙니다). 섹션이 `display:contents` 로 풀려 안의 카드가
격자 칸을 직접 받는 화면(설정)은 카드마다 `data-mode` 를 답니다 — 섹션을 탭마다 쪼갤 필요가 없습니다.
탭 줄·고른 탭 기억(탭 하나의 sessionStorage)·방향키·`aria` 는 셸(`SM`)이 한 벌로 그리므로 뷰는 탭 줄을
짓지 않습니다. `modes` 가 없는 화면은 탭 줄 없이 예전 그대로 섭니다.

- `count` — 탭 배지가 읽을 페이로드의 점 경로입니다. 값이 0 이면 배지가 없고, 첫 탭이 0 이면 다음 탭이 먼저 섭니다.
- 탭 점 — 건수가 아니라 "여기 할 일이 남았다"는 표시입니다. 화면이 자기 판정으로 `SM.setModeDot(화면, 탭, 켬)`
  을 부릅니다(선언에는 없습니다). 배지와 한 탭에 같이 설 수 있습니다.
- `hide_empty` — 보일 카드가 없는 탭을 탭째 접습니다. 로컬 전용·호스팅 전용 칸만 있는 탭이 그 배포에서 비는
  경우입니다(마크업에 카드가 하나도 없는 탭을 선언하는 것은 여전히 안 됩니다). 칸이 늦게 서거나 감춰지면
  화면이 `SM.modeApply(화면)` 을 다시 부릅니다.
- 화면이 대신 고른 탭 — 처음 열 때 할 일이 있는 탭처럼 화면 판정으로 서는 탭은 `SM.setMode(화면, 탭, false, true)`
  로 고릅니다(사람이 고른 것이 아니라 기억에 적지 않습니다). 사람이 누르면 셸이 `sm:mode` 를 알립니다.
- 칸으로 가기 — 대상 카드가 접힌 탭에 있으면 `SM.modeOf(요소)` 로 탭을 알아내 `SM.setMode` 로 먼저 엽니다
  (`goSee` 가 그렇게 합니다).

## 처리 큐 (queue)

열린 기회를 **한자리에서 처리**하는 목록(줄·보드, 상태 거르개, 종류 칩, 오른쪽 서랍, 상태 바꾸기, 요청문)은 셸의
부품 한 벌(`SM.queue`)이다. 화면은 큐를 짓지 않고 `view-def` 에 선언만 한다:

```json
"queue": {"kinds": "*"}                 // 모든 종류 — [개요]
"queue": {}                             // 이 화면이 see 로 가리키는 종류만 (= {"kinds": "see"})
"queue": {"mode": "work", "title": "처리"}   // 선택: 화면 modes 의 탭에 서고(그 탭 id), 제목을 바꾼다
```

종류 목록은 뷰에 적지 않는다. 어느 종류가 어느 화면 몫인지의 정본은 `scoring.KINDS` 의 `see` 이고, 서버가 그걸 뒤집어
페이로드(`queue_kinds_by_view`)로 싣는다 — `see` 가 없는 종류는 어느 화면 큐에도 안 들고 [개요] 큐에만 선다. 그런 종류는
의도한 예외여야 하고(`test_modes_assign.NO_HOME`), 지금 예외는 없다 — 새 종류를 만들면 `see` 부터 단다. 큐 카드는 셸이
화면 상자(머리 바로 아래)에 세운다. 자리를 정하고 싶으면 마크업에 `data-queue-host="<화면 id>"` 요소를 두면 그 안을 채우고,
종류 도넛은 `data-q-slot="kinds"` 빈 칸이 있을 때만 거기 선다(없으면 목록 위 칩 줄). 상태·거르개·서랍은 큐가 한 벌로
갖는다 — 화면은 `QU("<화면 id>")` / `SM.queue.of(id)` 의 이름 있는 메서드(`openById`·`reset`·`drawerExt` …)로만 부른다.
선언의 모양과 구현이 한 곳뿐이라는 것은 `test_seams` 의 180번대가 지킨다.

## 화면이 아닌 것

| | |
|---|---|
| [기회 카드](opportunity-card.md) | 여덟 화면에 똑같이 뜨는 한 벌짜리 부품 — 접으면 "무엇부터 왜", 펼치면 "어디를 어떻게", 그리고 AI 에게 그대로 넘길 요청문 |

기회 카드를 화면마다 설명하지 않고 여기 한 장으로 둔 이유는, 그것이 여덟 화면에서
같은 부품이기 때문입니다. 화면마다 적으면 여덟 벌이 되고 버튼이 바뀔 때 한쪽만 낡습니다.

문서의 사실은 전부 코드에서 확인한 것입니다. 각 장 맨 끝에 근거(파일·줄)가 HTML
주석으로 남아 있습니다 — 화면이 바뀌면 그 자리부터 다시 보면 됩니다.
