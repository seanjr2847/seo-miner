# ADR 0002 — 호스팅 런 결과가 릴리스 게이트다

## 상태

채택 (2026-09-02)

## 맥락

로컬 검사 226개가 전부 초록인 채로, 호스팅(Railway)의 자동 런 3회(8/30, 9/1, 9/2)
에서 유료 단계(rank·metrics·competitors·backlinks)가 통째로 실패했다. 증거는
서버 brain 의 `runs.notes` 에 그대로 남아 있었다 — `errors=100`, `updated=0`.
아무도 못 봤다.

못 본 이유는 검사가 게을러서가 아니라 **보는 곳이 다르기 때문**이다. 로컬 검사는
"계산이 맞다"를 본다(내 머신의 임시 brain 으로). 호스팅 런은 남의 컨테이너에서
남의 brain 에 쓴다 — 로컬에는 그 런이 아예 존재하지 않는다. 리포 안만 보면 알
방법이 없는 상태가 있다는 점에서 ADR 0001 과 같은 종류의 함정이다.

같은 날 두 번째 사고: main 에 push 하자 Railway 자동 배포가 돌았고, 그때 돌던 런이
죽었다. 워커는 subprocess 라 컨테이너와 함께 사라진다. push 하는 사람은 서버에서
뭐가 도는지 볼 창이 없었다.

## 결정

- **호스팅 런 결과를 릴리스 게이트로 만든다.** `skills/capture/scripts/test_remote.py`
  가 진짜 호스팅 서버에 묻는다 — `/api/run/status` 로 "지금 도는가", `/api/sql` 로
  "마지막 체인이 성공했는가"(`errors=N`, 유료인데 `api_calls=0` 이고 건너뜀 표식도
  없음, `finished_at IS NULL`). 하나라도 걸리면 FAIL 이다.
- **릴리스의 0번 다리다.** version 범프보다 먼저 `python run_checks.py remote` 를
  돌린다. 도는 런이 있으면 push 하지 않는다(재배포가 그 런을 죽인다). 마지막 런에
  실패 단계가 있으면 그것부터 본다.
- **없는 것과 못 닿는 것은 실패가 아니다.** `~/.capture/remote.json` 이 없으면
  건너뛰고(CI·남의 머신에는 물어볼 서버가 없다), 네트워크 오류·401 은 "확인 불가"로
  찍고 통과한다. 비행기 안에서 커밋을 못 하게 만드는 검사는 곧 꺼진다.
- **유료 단계 목록은 `run_all.STAGES` 의 `is_paid` 에서 읽는다.** 사본을 안 만든다.
- **HTTP 는 `remote.py` 의 `api()` 를 그대로 쓴다.** Bearer·401 해석을 두 벌 만들지
  않고, 그 덕에 `test_seams.py` 12번(원격이 부르는 `/api/*` 가 서버에 있는가)이 이
  파일도 함께 본다.

## 결과

- 릴리스는 네 다리가 된다: 호스팅 확인 → version 범프 → push → 설치 캐시 갱신.
- 초록불의 뜻이 바뀐다. 전에는 "내 머신에서 계산이 맞다"였고, 지금은 거기에
  "호스팅에서 마지막 런이 성공했다"가 붙는다.
- 이 검사는 실패를 **고치지 않는다** — 보이게만 한다. `errors=100` 의 원인(키 만료,
  쿼터, 프로바이더 장애)은 매번 다르고, 그 판단은 사람이 한다.

## 후속 (2026-09-04) — 그 `errors=100` 의 원인

쿼터였다. DataForSEO 문서: "Live endpoints are subject to a rate limit of 12
requests per minute per account." 우리가 부르는 DataForSEO 경로는 SERP·Labs·볼륨·
백링크까지 전부 `/live` 다. 그런데 간격은 러너의 항목 간격(0.5초)뿐이었으니 분당
120회, 한도의 10배를 던졌다. 게다가 429 는 `FATAL_STATUS` 에 없어서 "오류 한 건"으로
세어지고 0.5초 뒤 다음 키워드를 쳤다 — 한도는 계정 전체라 나머지도 전부 429 였고,
그래서 `errors=100`(키워드 상한과 같은 수), `updated=0` 으로 끝났다.

고침은 `serp_adapter` 한 곳이다: DataForSEO 호출 넷이 전부 `_dfs_call` 을 지나며
간격(분당 12회 = 5초)을 지키고, 429 면 기다렸다 다시 치고, 그래도 막히면 Fatal 로
단계를 끝낸다(그때까지 모은 것은 남는다). 429 를 `FATAL_STATUS` 에 넣는 것은 틀린
고침이다 — `raise_for` 는 제공자를 안 가려서 OpenRouter(AI 인용)까지 429 한 번에
멈춘다. 그건 쉬면 낫는 항목 단위 실패다.
