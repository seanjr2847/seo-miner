# 요청문 업그레이드

붙여 넣은 요청문 하나를 증상으로 보고, **그 요청문을 만든 생성기**를 고친다. 요청문
문장을 손으로 다듬는 게 아니다 — 같은 꼴의 요청문이 수백 건 나가므로 원인을 고쳐야 한다.

이 리포의 요청문 하자는 대부분 **파일 하나만 보면 멀쩡한** 종류다: 꼴(shape)과 처방(play)이
따로 정해지고, 절은 조건부로 서는데 가리키는 문장은 늘 실린다. 그래서 문장을 찾아 고치는
것으로 끝내지 않고, 그 문장이 **왜 그 갈래로 왔는지**까지 간다.

## 실행 모드

혼합. 진단·수정·릴리스는 메인이 직접 하고(사용자와 주고받고, 작업 트리를 고친다), 원인 추적과
검토는 서브에이전트에 맡긴다 — 추적은 큰 파일 셋을 읽어 메인 맥락을 아끼려고, 검토는 고친
사람과 다른 눈이 필요해서다. 서로 대화할 일이 없으니 지속형 에이전트는 쓰지 않는다.

| 단계 | 누가 | 산출물 (`_workspace/brief/`) |
| --- | --- | --- |
| 0. 맥락 확인 | 메인 | — |
| 1. 다시 뽑기 + 하자 목록 | 메인 | `00_before.md`, `payload-<project>.json`, `01_main_defects.md` |
| 2. 원인 추적 | 서브에이전트 `brief-tracer` | `02_tracer_causes.md` |
| 3. 실패 테스트 → 수정 | 메인 | 코드·테스트 변경 |
| 4. 다시 뽑기 + 검토 | 메인 + 서브에이전트 `brief-reviewer` | `03_after*.md`, `04_reviewer_verdict.md` |
| 5. 보고 → (승인 시) 릴리스 | 메인 | 커밋·push |

`_workspace/` 는 `.gitignore` 에 있다. 사후 확인용으로 남긴다.

## 0. 맥락 확인

- `_workspace/brief/` 가 있고 사용자가 "보완", "그거 말고 이것도"처럼 이어 말하면: 기존 파일을 읽고
  필요한 단계만 다시 한다(대개 3~4).
- 새 요청문을 받았으면: 기존 `_workspace/brief/` 를 `_workspace/brief-<YYYYMMDD-HHMM>/` 로 옮기고 새로 한다.
- `git status` 를 본다. 이번 일과 무관한 미커밋 변경이 있으면 기억해 두고 **커밋에 섞지 않는다**.

## 1. 다시 뽑기 + 하자 목록

붙여 넣은 요청문은 **옛 코드**로 만든 것이다. 이미 고친 하자를 다시 고치지 않도록 지금 코드로
같은 기회를 다시 뽑아 둘을 견준다.

1. 요청문에서 사이트와 기회 번호를 찾는다. 기록 명령 줄(`createdb.py done <project> <번호>`)이나
   `opp-<번호>.md` 에 있다. 없으면 사용자에게 묻지 말고 2번으로 건너뛴다(붙여 넣은 글만으로 진단).
2. 다시 뽑는다 — 페이로드를 저장해서 고친 뒤에도 같은 데이터로 견준다:
   ```
   python .claude/skills/brief-upgrade/scripts/render_brief.py <project> <번호> \
     --payload _workspace/brief/payload-<project>.json --out _workspace/brief/00_before.md
   ```
   호스팅 사이트는 서버의 페이로드를 받아 **로컬 코드로** 다시 조립한다(서버가 실은 o.brief 는 버린다).
   이 PC 의 파이썬 경로·인코딩은 메모리의 python 항목을 따른다.
3. `references/defect-classes.md` 로 붙여 넣은 글을 훑어 하자를 적는다. 하자마다: 번호 · 분류 ·
   인용(요청문의 그 줄) · 왜 하자인지 한 줄 · 다시 뽑은 글에서도 남는지(남음/이미 사라짐).
   사용자가 "하자가 많다"고만 했으면 전부 찾는다. 콕 집은 게 있으면 그것부터, 나머지는 덧붙인다.
4. `01_main_defects.md` 에 쓴다. 다시 뽑은 글에서 전부 사라졌으면 여기서 멈추고 "배포가 안 됐을
   뿐"이라고 보고한다(호스팅이 옛 버전인지 `plugin.json` 버전과 최근 배포로 확인).

**붙여 넣은 요청문 없이 "알아서" 훑으라고 하면:** 사이트마다 `render_brief.py <project> --list
--payload …` 로 열린 기회를 (종류 · 꼴 · 갈래 · 페이지 유무)별로 보고, 갈래마다 대표 하나씩 뽑아
`00_before-<site>-<번호>.md` 로 다시 뽑는다. 이상해 보이는 조합(순위 기회인데 페이지 없음, '밀림'인데
페이지 없음, 새 글 꼴인데 페이지 있음)을 먼저 고른다. 닫힌 기회는 `--list` 에 안 나온다 — 닫힌 걸로
진단하면 이미 닫힌 일을 고친다. 요청문 본문은 `## 답의 형식` 앞까지만 읽어도 된다(꼬리는 꼴마다 같다).

## 2. 원인 추적 — `brief-tracer`

```
Agent(subagent_type: "brief-tracer", prompt: "하자 목록: _workspace/brief/01_main_defects.md
다시 뽑은 요청문: _workspace/brief/00_before.md, 페이로드: _workspace/brief/payload-<project>.json
원인별로 묶어 _workspace/brief/02_tracer_causes.md 에 써라.")
```

결과를 받으면 원인마다 메인이 직접 해당 코드를 열어 확인한다 — 추적 결과를 그대로 고치기
목록으로 쓰지 않는다. 일부러 정한 동작을 뒤집는 원인이면, 그 주석이 막으려던 실수가 수정 뒤에도
안 나는지를 3단계 테스트에 넣는다.

원인이 둘 이상이고 그중 하나가 크면(새 꼴·새 페이로드 필드·화면 이음매) 사용자에게 범위를 한 줄로
묻는다. 작으면 묻지 않고 전부 고친다.

## 3. 실패 테스트 → 수정

- 원인마다 `skills/capture/scripts/test_brief.py` 에 테스트를 먼저 쓰고 **FAIL 을 확인**한다.
  테스트는 하자 문장이 없어지는 것만 보지 말고, 그 자리에 있어야 할 것(맞는 꼴·맞는 후보)을 같이 본다.
- 기존 테스트가 옛 동작을 못 박고 있으면 고친다. 이유를 테스트 주석에 남긴다(이 리포의 관례다:
  "예전엔 … 했다 — 그래서 …").
- 코드 주석도 같은 관례로 쓴다. 무엇이 실제로 나갔는지(사이트·검색어)를 적는다.
- 쓸모가 없어진 문장·필드(예: 처방의 `deliver_new`)는 지운다. 남기면 다음 사람이 그 갈래가 산다고 읽는다.
- 화면 쪽에 같은 목록·문장이 있으면(폴백 요청문, `shapes_payload`) 이음매다 — CLAUDE.md 「이음매는
  양쪽 끝을 함께 검사한다」를 따른다. 화면 파일을 고쳤으면 CLAUDE.md 대로 브라우저로 연다.
- 끝나면 `python run_checks.py` 전부. 실패를 숨기지 않는다.

## 4. 다시 뽑기 + 검토 — `brief-reviewer`

1. 같은 페이로드로 다시 뽑는다: `--payload` 는 그대로, `--out _workspace/brief/03_after.md`.
2. 수정이 다른 갈래를 건드렸으면 그 갈래 시나리오도 뽑는다. 같은 페이로드에서 같은 종류의 다른 기회
   번호를 골라 `03_after-<번호>.md` 로. 실데이터에 없는 갈래는 테스트의 ctx 로 `brief.text()` 를 찍는다.
3. 검토를 맡긴다. 고친 경위는 넘기지 않는다:
   ```
   Agent(subagent_type: "brief-reviewer", prompt: "요청문: _workspace/brief/03_after*.md
   고치기 전 하자 목록: _workspace/brief/01_main_defects.md
   판정을 _workspace/brief/04_reviewer_verdict.md 에 써라.")
   ```
4. `남음` 이 있으면 3단계로 돌아간다. 두 번 돌아도 남는 건 '고치지 않은 것'으로 보고한다.

## 5. 보고 → 릴리스

보고는 짧게: 원인마다 무엇이 문제였는지(하자 여러 개 → 원인 하나로 묶어서), 무엇을 고쳤는지, 검사
결과, **고치지 않은 것**(데이터 문제, 범위 밖, 다음 순서). 그리고 "커밋하고 배포할까요?"로 끝낸다.
승인 없이 커밋·push 하지 않는다.

승인하면 CLAUDE.md 「릴리스는 세 다리다」가 정본이다. 그 위에 이 PC 에서 겪은 두 가지를 더한다:

- **0번 다리는 둘 다 본다.** `run_checks.py remote` 는 이 PC 계정의 사이트만 본다. Railway 로그
  (프로젝트 `9c04ccb7-5316-4e84-968a-193f40f05628`, 서비스 `c4457167-6166-41ec-804f-00b31243404e`)를
  `"수집 시작:" or "수집 결과 (" or "[resume]"` 로 거르고, 마지막 결과 이후의 `수집 시작:` 이 없는지
  본다. limit 에 걸려 잘리면 시작 시각을 당겨 다시 읽는다.
- **커밋은 이번 파일만** `git add <경로>` 로. `plugin.json` 은 패치 버전을 올린다(`skills/` 가 바뀌었으므로).
- **플러그인 갱신은 설치된 프로젝트마다** `--scope project` 로, 그 프로젝트 디렉터리에서 실행한다.
  끝나면 `~/.claude/plugins/installed_plugins.json` 의 버전으로 확인한다. 폴더가 사라진 설치는 건너뛰고 보고한다.

## 오류 처리

- `render_brief.py` 가 "기회가 페이로드에 없다"고 하면: 닫힌 기회다. 붙여 넣은 글만으로 진단하고,
  같은 종류·같은 갈래의 열린 기회를 찾아 그걸로 다시 뽑는다.
- 원격 인증 실패(`remote.py connect` 를 다시 하라는 메시지)는 다시 시도하지 않는다. 사용자에게
  `! python skills/capture/scripts/remote.py connect …` 를 안내하고, 그동안은 테스트 ctx 로 진행한다.
- 서브에이전트가 실패하면 한 번 다시 부르고, 또 실패하면 메인이 그 단계를 직접 한다. 결과 파일에 그렇게 적는다.
- 추적 결과와 메인의 확인이 다르면 지우지 말고 둘 다 `02_tracer_causes.md` 에 남긴다.
